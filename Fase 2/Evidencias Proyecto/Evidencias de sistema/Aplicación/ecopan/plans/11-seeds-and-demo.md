## 1. Seed mechanism

- **Versioned seed files**, one directory per tenant profile: `backend/app/src/main/resources/seeds/panaderia-centro/` and `.../unipan/` (JSON; YAML rejected — one less parser, kotlinx-serialization already present). Each profile = one `profile.json` with a `seedVersion: Int`.
- **Loader** lives in `backend:app`: **boot-time only (DECIDED, `01` §7)** — `02` §7's `SEED_PROFILE` env var takes a **comma-separated list** of profile names (`SEED_PROFILE=panaderia-centro,unipan` seeds both tenants in one boot); each named profile loads idempotently at startup (`02` work item 8). No admin seed endpoint, no CLI path. **Demo reset = backend restart** — the idempotent boot hook re-converges state; rehearse the restart once so its duration is known (§4 contingencies, `10` §9). Reconciled: the profile files live where `02` expects them (`backend/app/src/main/resources/seed*/…` — align the exact directory name with `02`'s loader when implemented).
- **Idempotent + re-runnable:** every seeded row carries a fixed UUID **declared in the seed file** (not generated at load). Loader upserts by ID; unchanged rows are no-ops. Re-running after `azd down`/`up` restores identical state (`10` §9 depends on this). Stock **movements** are append-only, so seeded opening movements also have fixed UUIDs — idempotent upsert prevents double-counting. `seedVersion` recorded per tenant; loader refuses to apply an older version over a newer one.
- Passwords **and PINs** appear in seed files as **plaintext for the demo repo** (both hashed by the loader at insert — bcrypt, per `02` §2; the `pin` is each user's device-unlock credential per `01` §4). Acceptable: demo creds only, stated openly.
- **Synthetic sales history** (demo-only, spec §9): generated by `ml/`'s synthetic generator (`08-ml-forecasting.md`), exported as `sales-history.json` (a list of Sale/SaleLine rows with fixed UUIDs, ~90 days, per branch/product), referenced from `profile.json` as an optional include. Loaded only for tenant A (feeds dashboard KPIs + forecast chart). Never used in ML evaluation — that is Favorita-only per `08`.

Seed file shape (contract):

```json
{
  "seedVersion": 1,
  "tenant": { "id": "…", "name": "Panadería Centro", "currencyCode": "CLP",
              "enabledModules": ["POS_SALES","INVENTORY_FORMULAS","DEMAND_FORECASTING","MULTI_BRANCH_ROLES","ANALYTICS_DASHBOARD"] },
  "branches": [ { "id": "…", "name": "Casa Matriz" } ],
  "users": [ { "id": "…", "username": "vero", "password": "demo-vero-1", "pin": "2468", "role": "GENERAL_MANAGER", "branchId": null } ],
  "products": [ { "id": "…", "name": "Marraqueta", "productType": "MARRAQUETA", "soldBy": "WEIGHT", "pricePerKgMinor": 2200 } ],
  "formulas": [ { "productId": "…", "lines": [ { "ingredientId": "…flour", "basisPoints": 10000 }, { "ingredientId": "…water", "basisPoints": 6500 } ] } ],
  "dayOldPolicies": [ { "productId": "…", "mode": "DISCOUNT", "discountBp": 5000 } ],
  "ingredients": [ { "id": "…", "name": "Harina", "lowStockThresholdGrams": 10000000 } ],
  "openingStock": [ { "movementId": "…", "ingredientId": "…flour", "deltaGrams": 50000000, "kind": "PURCHASE" } ],
  "salesHistoryFile": "sales-history.json"
}
```

(Amounts: integer minor units, CLP zero-decimal; mass integer grams — `01` §5. `basisPoints` = basis points of flour weight; `discountBp` = discount in basis points, per `02`'s `day_old_policies.discount_bp`. Ingredients carry no unit field — grams always, `01` §5 / `02` §1. Field names track `02` §1's columns camelCased.)

## 2. Tenant profile A — "Panadería Centro" (reference client, central Chile)

- **1 branch** (Casa Matriz). Currency CLP. **All 5 modules ON.**
- **Users:** `vero` GENERAL_MANAGER (the baker-owner; also logs batches — role gives her everything incl. production destinations per `01` §1), `caja1` CASHIER (branch-scoped). Plus `admin` ADMIN for toggles. Every user carries a distinct 4-digit `pin` (device unlock/switch, `01` §4) alongside the password.
- **Products:** weigh-and-sell breads — Marraqueta, Hallulla, Pan Amasado, Dobladita (`soldBy=WEIGHT`, `pricePerKgMinor` ~1800–2600) + 3 resale barcode products (`soldBy=UNIT`, with `barcode`): bottled drink, empanada (bought-in), butter pack.
- **Formulas (baker's %, bp of flour=10000):** for Marraqueta, Hallulla, Pan Amasado, Dobladita — flour 10000, water ~6000–6500, salt ~200, yeast ~100–150, fat (hallulla/amasado) ~800–1500. Illustrative; exact bp values are seed data, not decisions.
- **Day-old policies:** Marraqueta → `DISCOUNT 50%`; pastries/dobladita → `DISCARD`. (Illustrative pairing for the forecasting narrative: discard = loss, discount = partial recovery.)
- **Ingredients + opening stock:** harina 50 kg, agua (tracked or untracked — decide with `06`, flag), sal 5 kg, levadura 2 kg, manteca 10 kg — as opening `PURCHASE` movements.
- **Synthetic history:** 90 days of sales for the branch across all products (weekday/weekend seasonality baked in by the generator) → dashboard KPIs + forecast chart have something to show.

## 3. Tenant profile B — "UniPan" (the genericity proof, spec §7)

Structurally different bakery stood up by **config only — zero code change**. This seed *is* the capstone's genericity metric.

- **Unit-sold only:** every product `soldBy=UNIT` (pan de molde, bagels, cookies, sandwiches). **No scale anywhere in its flow.**
- **3 branches** (Norte, Centro, Sur) — exercises `MULTI_BRANCH_ROLES` for real.
- **Users:** 3 × BRANCH_MANAGER (one per branch, `branchId` set), 1 GENERAL_MANAGER (`branchId=null`), cashiers per branch, **no BAKER users needed** (resale-style shop).
- **Modules:** `DEMAND_FORECASTING` **OFF**; `INVENTORY_FORMULAS` **OFF** (optional per task brief — take the stronger proof: off) → **no formulas, no ingredients, no opening stock in the seed at all**. `POS_SALES`, `MULTI_BRANCH_ROLES`, `ANALYTICS_DASHBOARD` on.
- **No day-old policies** (or a single `DISCARD` to show the surface exists — default: none; empty is the point).
- No synthetic history needed (dashboard shows live-demo sales only) — keeps the seed tiny and visibly different.
