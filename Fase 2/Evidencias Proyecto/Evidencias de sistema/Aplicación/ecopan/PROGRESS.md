## Decisions from the 2026-09 team review

Three action points from the September team review, and what happened to each:

1. **Formulas are entered in kilos per kilo of flour, not percentages** — ↪️ deviation from plan 07
   §5 row "Formulas editor" / §10 test surface 1. The wire format is untouched (basis points
   relative to flour, 10000 = flour; every client, the worker and the seeds are as they were), only
   the web editor reads and writes `bp / 10000` (`lib/format.ts`'s `bpToKgPerKgFlour`). The
   preview now asks for the **flour** weight and lists every ingredient in kg plus the total dough
   — still derived by the exact ledger algorithm on that total, so the "web display and KMP ledger
   provably agree" property of §10 holds. Reason: the bakery weighs everything in kilos, and
   "peso de la mezcla a probar" as a total-dough input read as nonsense to the people using it.

2. **Day-old bread — discount path removed.** The goal is to *know how much bread is not sold the
   same day*, not to sell it differently: no discount, no separate product, no distinction at the
   counter. That rules out every till-side approach, because tracing at the point of sale would
   need the cashier to tell yesterday's loaf from today's on every sale, which is not realistic.
   The code built for the discount path was therefore deleted rather than left idle: the
   `DayOldPolicy` entity/table/DTOs/C7 routes and its `DAY_OLD_POLICY` sync entity, the K4
   `day-old-loss` analytics, the `isDayOld`/`dayOldDiscountBp` sale-line columns and wire fields
   (backend, Room — schema 10 drops them via AutoMigration — and the sale push payload), the Room
   entity/DAO/converter, the client repositories and appliers, the two web pages, and the seeds.
   Booting an existing Postgres runs an idempotent retire step that drops the table and the two
   columns. ↪️ deviation from plans 01/02/03/05/07 §day-old and `spec/SPECS.md` (left as written:
   they are the record of what was designed). If the carry-over number is still wanted, the
   realistic capture point is a closing count — what is left per product at end of day, entered
   once by the baker or manager, reconciled against that day's batches and sales.

3. **Stock for resold products (drinks, groceries) — added.** Products could already be created
   but had no stock. Now: a second, separate unit ledger (`product_stock_movements`, web-only, no
   `server_seq`, not synced) with `GET /inventory/product-stock`, `GET|POST
   /inventory/product-movements`; the *Ingreso de stock* page gained an **Insumos | Productos** tab
   so the same purchase / adjustment / ledger view serves both; and a new **Stock de productos**
   dashboard page sits beside (not inside) the ingredient stock page, per the review's "two
   distinct groups, keep them apart" reasoning. Only `UNIT` products are accepted
   (`PRODUCT_NOT_UNIT` otherwise). Sales are never written as movements: current stock is
   Σ movements − `sale_lines.quantity` sold **since the product's first movement**, so a product
   starts being counted the moment someone first records it and old sales don't drag it negative.
   A low-stock threshold per product has since been added (see "Reorder level" below). *Superseded
   by "Almacén stock lives on the product" (#24): stock is opening count + movements − sales since
   the opening count, shown on the product, and no longer behind `INVENTORY_FORMULAS`.*

### Reconciled inventory report — HU-ANA-0006 (added 2026-10)

`GET /inventory/reconciliation?branchId&from&to` (`YYYY-MM-DD`, inclusive, day bounds in the
reporting timezone; `STOCK_READ` + `INVENTORY_FORMULAS`) returns per ingredient the opening balance
(Σ before `from`), Σ purchases, Σ formula decrements, Σ manual adjustments, closing, and the
distinct-batch count behind the decrements — one grouped query
(`StockMovementRepository.reconcileByIngredient`). Opening + movements = closing by construction;
for a range ending after the last movement, closing equals `GET /inventory/stock`. Web:
**Análisis → Inventario reconciliado** (`analytics/reconciliation`) with branch + date pickers
(default: the last 30 reporting-timezone days), totals row, kg-to-the-gram display and a CSV export
in exact grams (text cells starting `= + - @ tab CR` are apostrophe-prefixed against spreadsheet
formula injection). Ingredients with no movement before `to` are omitted; a ledger row whose
ingredient is missing from the catalog is kept with an empty name (the page shows "Insumo sin nombre"; an id is never shown). A range is at most 366 days
within 2000-01-01…2200-12-31, else `INVALID_DATE_RANGE`. Out of scope as specified: expected usage
from sales × formula, physical counts.

The response is `{ batchCount, rows[] }`. `batchCount` is the period's **distinct** batches
(`StockMovementRepository.countDecrementBatches`); the web total row and CSV total use it. Each
row's own `batchCount` stays per ingredient and must never be summed: one batch decrements every
ingredient in its formula (3 batches x 4 ingredients summed to 12).

Two limits worth knowing, both pinned by tests (`StockMovementRepositoryTest`):
- **Closing equals current stock only if nothing is dated after the end of the range.** Current
  stock sums every movement; a report ending today stops at the end of today, so a future-dated
  movement (a skewed device clock) shows in stock but not in the report.
- **A past period can change.** Movements are placed by `occurred_at`, not by when they arrived, so
  a backdated entry synced from an offline device later alters the opening/closing of periods already
  reported. Re-run the report to see the settled figures.

`stock_movements` also gained `(tenant_id, branch_id, occurred_at)` for the opening-balance scan
(declared on the table and created `IF NOT EXISTS` for databases booted before it).

### Almacén stock lives on the product (spec #22, slice #24 — closed 2026-10-04)

Supersedes "Stock for resold products" and "Reorder level for resold products" above (their
mechanics stay, their *surfaces* moved).

- **Math.** Product stock = opening count + purchases/adjustments − units sold. A new
  `OPENING_COUNT` kind in `product_stock_movements` carries the opening count; the branch's earliest
  one is where sale counting starts (`trackedSince`), replacing the old "since the first movement"
  rule. A branch with no opening count counts from the product's creation.
  *Clock semantics (#41):* everything is on the server clock. `trackedSince` is the server receipt
  time (`received_at`) of the opening count, i.e. when it was entered, not its client-supplied
  `occurred_at`; a sale counts iff the server received it (`sales.received_at`) at or after that
  instant, whatever its `soldAt`. So an offline sale rung up before the count but synced after it
  IS subtracted; a sale received before the count is NOT (the shelf count already reflects it),
  even if the count is backdated. Seeded sales are "received" at their `soldAt`, so seeded history
  never counts against a later opening count. Analytics keep using `soldAt`. Negative stock is legal
  (`currentUnits < 0`): reported at API and UI, never blocking.
- **API.** `POST /catalog/products` takes `openingStock` (required for Almacén, 0 allowed;
  `OPENING_STOCK_REQUIRED` / `INVALID_OPENING_STOCK`) and `openingBranchId` (defaults to the caller's
  branch; `OPENING_BRANCH_REQUIRED` for an all-branch caller with none, `BRANCH_FORBIDDEN` across
  branches). Validated before the product row is written; the product insert and its opening movement are one
  repository transaction (`CatalogRepository.createProduct(opening = ...)`), so a failure leaves no
  product without a count. The opening movement id derives from the product id. `GET /inventory/product-stock` now lists *every*
  Almacén product in the branch (not only those with a movement). Movement/threshold endpoints refuse
  non-Almacén products with `PRODUCT_NOT_ALMACEN` (was `PRODUCT_NOT_UNIT`); `OPENING_COUNT` cannot be
  posted by hand. Wire shape of `ProductStockLevelDto` is unchanged; sync pull is untouched.
- **Gate.** `product-stock` and `product-movements` left `INVENTORY_FORMULAS`; only `ingredients`,
  `stock` and `movements` keep it. Permissions are as before (`STOCK_READ`/`STOCK_ADJUST`).
- **No baseline migration.** There is no legacy data to baseline: the seed profile carries an explicit
  `openingCounts` per branch for every Almacén product (unipan: 40/30/20), appended idempotently by the loader.

### Till shows Almacén stock badge (spec #22, slice #26 — closed 2026-10-04)

- **Pull.** `ProductPullPayload` gained two optional fields: `lowStockThresholdUnits` (Almacén only) and
  `stockUnits` — current stock *in the pulling principal's branch* (same math as
  `GET /inventory/product-stock`, negative allowed). The pull is tenant-scoped, so the branch comes from
  the JWT (`SyncPullService.pull` now takes `principalBranchId`); an all-branch principal or a Panadería
  product carries no `stockUnits`. Older clients ignore the new keys, new clients read their absence as
  "unknown".
- **Why stock re-syncs.** Stock is derived (ledger + sales), so the product row never changed when it
  moved and a cursor pull would never re-send it. A product-stock movement or a sale line for an Almacén
  product now bumps that product's `server_seq` (`bumpAlmacenProductSeq`, one `nextval` per row, same
  transaction). Cost: a sale at any till re-pulls that product at every branch's till (one small row).
  Not bumped: the bulk `createAllWithLines` seed path. A device that enrols or reconnects as another
  branch's user runs a full `bootstrap()` pull, so it does not keep the old branch's figure.
- **Bug fixed on the way.** `SyncPullRepositoryImpl.toProduct` never set `origin`, so every product
  went out on the wire as `PANADERIA` despite #23/#25; now it reads the column.
- **Clients.** Room v12 (`AutoMigration(11, 12)`; `products.lowStockThresholdUnits`, `products.stockUnits`,
  both nullable, `12.json` exported) → `ProductUpsert`/`Product` → `ProductSyncApplier`.
- **Local sales since the last sync.** `ProductRepositoryImpl` shows `stockUnits` = pulled figure minus
  units in sales whose outbox row is still `PENDING`/`IN_FLIGHT` (`SaleDao.observeUnsyncedUnitsByProduct`),
  computed on read — never written back, so a re-pull cannot double-count. `FAILED` (rejected) sales are
  not subtracted. A null pulled figure stays null (no badge).
- **Till.** `PosProductUi.stockBadge` (`Product.stockBadge`, `:jvm:feature:pos`): negative (< 0), out
  (== 0), low (<= reorder level, > 0), otherwise none; none for Panadería, no reorder level (low only),
  or no figure yet. Stale-offline = sync indicator `OfflinePending`/`Attention`: same level, drawn
  outlined with a "last sync" content description instead of filled. Adding a line and charging never read
  the badge: a sale at zero/negative completes (VM test).
- **Not done.** Baker mobile does not show stock; the web does not show the till's local view.

## What is done

**02 backend** — schema + repositories, auth (JWT, `requirePermission`/`requireModule`), all eight
routers (auth, tenant, catalog, inventory, sync, analytics, forecasts, events), sync push/pull with
idempotent re-push, seed loader, and both async pipelines. The inventory router also carries the
resold-product unit ledger (`product-stock`, `product-movements`), a web-only table outside the
synced domain set. The `ForecastRefreshProcessorImpl` stub is
gone: the worker now buckets 90 days of sale lines and calls the ML service for real, verified end to
end through RabbitMQ into `forecasts` and back out via F1. Forecasts also refresh themselves:
every worker replica ticks `DailyForecastScheduler`, and a `scheduled_runs` (job, local day)
unique-key claim lets exactly one publish `ForecastRefreshRequested` per branch of each
`DEMAND_FORECASTING` tenant after 00:05 `REPORTING_TZ` (plan 08's deferred "batch scheduling
mechanism", #46). The run is one-shot: a branch whose refresh fails at consume time (ML down) is
not retried -- RabbitMQ drops it, Service Bus dead-letters it -- and waits for the next night or the
GM's button. A worker killed after claiming a branch loses nothing: claims are 5-minute leases
with a `completed_at`, retaken on expiry. Pronóstico shows "Actualizado: …" and, for GM/ADMIN, an *Actualizar pronóstico* button.

### Closed value sets — enums + CHECK constraints (spec #22, ticket #31)

Payment method, sold by (products and sale lines), ingredient and product stock movement kind,
batch decrement status and product origin are Exposed `enumerationByName` columns (same varchars, same
names on the wire, KMP Room converters untouched), and `ClosedValueSets.kt` (backend/data) adds one
`ck_<table>_<column>` CHECK per column at boot, after the additive-DDL pass. It is idempotent (skipped
when the stored set matches the enum, recreated when the enum changed) and strict: a row outside a set
fails boot loudly (no `NOT VALID` / stray audit; reseed). Sync ingest now rejects an unknown payment method / sold by with
`VALIDATION_ERROR` naming the allowed values; stock-movement kinds were already `INVALID_KIND` (REST) /
`VALIDATION_ERROR` (sync). Tests: `ClosedValueSetConstraintTest` (Testcontainers) plus new Sync/Inventory/Catalog router tests.

### Roles as a lookup table (spec #22, ticket #32)

`roles` is a small table seeded at boot from the `Role` enum (the same five the web `can()` table keys on:
CASHIER, BAKER, BRANCH_MANAGER, GENERAL_MANAGER, ADMIN). `users.role` and `role_permissions.role` are foreign
keys to it (declared through Exposed `.references`) and `role_permissions.permission` is the `Permission`
enum by name with a `ck_role_permissions_permission` CHECK. API: unknown role on T3/T4 already answered `400 INVALID_ROLE`
(now pinned by router tests); there is no API that writes permissions, so that rejection is DB-level. Capability
checks and the web are unchanged. Tests: `RoleLookupConstraintTest` (Testcontainers) and two `TenantRouterTest` cases.

### Tenant modules in a join table (spec #22, ticket #33)

A tenant's enabled modules are rows of `tenant_modules (tenant_id, module)`: primary key per pair, `tenant_id`
a cascading FK to `tenants`,
`module` the `Module` enum by name with a `ck_tenant_modules_module` CHECK. `TenantRepository` reads/writes
only that table; the ~30s cached `enabledModules` lookup, session payload and Módulos page/API are unchanged
(unknown id on `PUT /tenant/modules` already answered `400 INVALID_MODULE`, now pinned by a router test; the
seed loader logs an unknown id instead of dropping it silently).
There is no legacy `enabled_modules` column anywhere in the model or boot code (demo data only: reseed).
Tests: a `TenantRouterTest` case (the migration test was removed with the migration).

### Fixed product types (spec #22, ticket #27; revised in #34)

`product_types (id, tenant_id, name, key)` stays (forecasts, analytics and the product FKs depend on it) but is
no longer manager-extendable: every tenant has exactly Pan, Pastelería and Almacén, created with the tenant
(`TenantRepositoryImpl.create`) and get-or-created by key for a tenant that predates that. `GET`/`POST
/catalog/product-types` and the web create-new UI are gone; the web picker is a plain `ChoiceSelect` over
`lib/productTypes.ts`. `key` is `ProductTypeKey.of(name)` (case/accent/spacing-insensitive, unique per tenant);
`products.product_type_id` and `forecasts.product_type_id` reference it, and the `product_type` varchar stays as
the canonical-name snapshot on the sync wire. Analytics and forecast series group on the key via
`ProductTypeSeries`. `products` has a composite FK `(tenant_id, product_type_id)` to `product_types(tenant_id, id)` (#42); `forecasts` has the same composite FK (#42). Tests: `ProductTypeLookupTest`
(Testcontainers: seeded types, FKs), `CatalogRouterTest`, `SeedLoaderTest`, `ProductFormDialog.test.tsx`,
`ProductsPage.test.tsx`.
